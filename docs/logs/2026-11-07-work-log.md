# ChatBridge 工作日志：DSH 原生生命周期验证

日期：2026-11-07（Asia/Shanghai）。接续[上一份工作日志](2026-11-06-work-log.md)。当前阶段仍为 M1，未进入 M2。

## 本轮动作

1. 从 Git 核对 `v0.0.0-m1.3` 工作日志和代码基线，复查已发布 DSH SDK/runtime；PyPI 候选仍为 `0.2.1rc2`，源码比较提交仍为 `fcc0ad4`。
2. 在标准 sdk profile 的临时 dsh_home 试验官方 bundle 管理路径。发现普通 patch 目标和外置模块路径不能代替 bundle 安装；新增注册完成标记，避免 SDK 成功启动却错误地认为守卫已加载。
3. 通过原生函数构造临时空历史权限覆盖，恢复后实际回读到 full-access，再降级为 workspace-write/never；主动拒绝的生命周期回调能让 SDK 恢复失败。
4. 程序化原生问题在本版本/profile 下返回 NO_PROVIDER，初始化的能力声明本身不足以证明问答往返。
5. 新增独立探针、仅供临时 home 的本地 bundle、脱敏报告和测试，初批提交 `2e9e0dd` 已推送。
6. 独立审阅发现 SDK 会把被过滤的 QQ 环境键从父进程重新合并。增加隔离 worker 和启动前清理，在官方 SDK Popen 边界先复现再修复；错误答案也改为明确失败。
7. 完整 64 项测试通过，Ruff、Python 格式、Node 语法和 Git 空白检查通过。最终探针仍退出 2，未把剩余真实验收改成完成。

## 本轮结论

- **已证明**：发布候选的本地 bundle 加载、原生策略函数、历史覆盖降级与生命周期主动拒绝路径可工作。
- **尚未证明**：首个模型请求的完整阻断、真实 Windows 文件写入边界、实际模型触发的问答/取消，以及 QQ 真机能力。
- **问答阻塞更明确**：本次声明 userQuestions 后仍返回 NO_PROVIDER；不能仅按 master 的高层回调示例冻结产品接口。
